# DR-281: A checkout writes line feeds whatever `core.autocrlf` says, and the checks read Windows line endings as git stages them

- **Type:** technical
- **Boundary:** inside
- **Reversibility:** reversible
- **Status:** accepted
- **Decided by:** the change `add-pr-cost-calculator`, as the owner asked on 2026-11-21
- **Requirements:** R176, R210, R255, R268, R269, R272, R274, R275, R276
- **Threats:** T143, T226, T251, T256, T267, T268, T269, T270, T273, T274, T275, T276, T277, T278
- **Replaces:** none
- **Closed by:** none

## Context

The owner asked on 2026-11-21 that the design not break with Windows line endings, since the project supports Linux, macOS and Windows. Git writes a carriage return before each line feed in a checkout where `core.autocrlf` is `true`, and an editor on Windows can save a file so. The repository tracked no attributes file, so each clone's line endings were left to the person's git, and the checks of single pages read each file as the working tree holds it, several of them refusing a carriage return before a line feed, as the test of characters of R268 would. In a trial with git 2.43.0 on 2026-11-21, a clone of this change's branch made with `core.autocrlf` set to `true` failed 17 of the 2773 tests, all of which passed in a clone made without it: tests of the checks of the backlog, the roadmap, the context files, the guide, the specs' form and the threat model, the test that runs the session's start hook, and the tests that run `scripts/sync-superpowers.sh`, which bash ended with an error, since it read the carriage return at the end of each line as part of the line. With one line of attributes that gave every file `text=auto` and `eol=lf`, such a clone held line feeds alone and passed every test. When each file that the repository writes, but its shell scripts, was then saved with a carriage return before each line feed and left unstaged, 10 tests failed, in the checks of the backlog, the roadmap, the context files, the guide, the specs' form and the threat model, though git would commit each such file with line feeds alone, and with the files under `openspec/` alone so saved, `scripts/verify-openspec.sh` failed as well. `.editorconfig` asks editors for line feeds (DR-116), but not every editor reads it.

The design-stage review of this decision found where line feeds in a checkout do not reach. Git writes only the files that a checkout changes, so a clone made with `core.autocrlf` set to `true` before the line keeps a carriage return before each line feed in every file that a later pull leaves alone, while `git status` shows nothing, and its start hook and scripts keep failing in bash. `.claude/settings.json` runs `vendor/superpowers/hooks/run-hook.cmd` with bash, though its name does not end in `.sh` and it does not start with `#!`. And `scripts/sync-superpowers.sh` writes and compares the vendored copy through `git archive`, which the repository's attributes do not reach and which follows the person's `core.autocrlf`: where that is `true`, its check reported a copy that matched upstream as differing, and a refresh wrote carriage returns into the vendored hooks, which bash then could not run.

The threat review against what was built found more. The sync refused `.git` in any case but wrote the names that Windows and HFS+ open as `.git`, which git's checkout refuses; a refresh deleted and wrote files through a link that the copy held; and the sync worked in the repository that an exported `GIT_DIR` names. The vendor check compared no modes, though the rule that knows `run-hook.cmd` for a script rests on its mode, and told a clone made before the line nothing of how to write the vendored copy again, while the way back that the test gave for a script threw away an edit not yet staged. A condition or `continue-on-error` could skip the job of Windows line endings, or let a step of it fail, while the job `ci` passed, and an attributes file that an update of upstream brings held the update up. The review lanes found that a refresh which stopped left the vendored copy deleted or written in part, since it deleted the vendored paths before it fetched, that a pinned file with a carriage return before a line feed passed the vendor check until git committed it with a line feed alone, and that the job of Windows line endings wrote through a folder that the working tree holds as a link and, run from a folder below the top of its working tree, into the vendored copy.

## Decision

One line of the repository's attributes gives every tracked file `text=auto` and `eol=lf`, so that git writes line feeds in each file that it checks out, whatever `core.autocrlf` says, though a person's own attributes, such as a `.git/info/attributes` that gives `eol=crlf`, still outrank the line. Git then stages a file that it reads as text with line feeds alone, unless git's index already holds that file with carriage returns, which it keeps, or `core.safecrlf` has it refuse the file, while a file that it reads as binary is staged as it is. Each check that reads the bytes of a file of this repository from the working tree takes each carriage return right before a line feed as a line feed, as git does when it stages a text file, through one function that the checks share, in every file but a script, a file whose name ends in `.sh`, that starts with `#!` or that git records as executable, which bash or the system reads with the carriage return as part of its line. A check that reads a file's text through Python's universal newlines, which already read such a carriage return as a line feed, stays as it is, and so does each reading of git's index and the comparison of the vendored copy with the bytes of its pinned commit, which a vendored file saved with Windows line endings fails. The test of characters still fails on a carriage return that git's index holds, on one that no line feed follows, and on any in a script, where it says to stage the script, delete it, check it out again and unstage it, which keeps an edit not yet staged, or to clone the repository again, the way back for a clone made before the line. A job of CI saves each file that the repository writes, but its scripts, with a carriage return before each line feed, reading git's index and the working tree as the test of characters does, so that it writes through no link, and stopping, with nothing written, on a folder below the top of its working tree, fails where it saved none, and runs every check that CI runs on a pull request on that working tree, and a test holds the job `ci`, for which a merge waits, to every job, and fails where a job but `ci` sets `if`, or where a job or a step sets `continue-on-error` or a step sets `if`. Each test that plants Windows line endings first checks that it meets them. The sync script of the vendored copy writes each file from the pinned commit's objects, with its bytes and its mode, and writes nothing else: it stops on a link or a submodule, and on a path that git's checkout refuses with the protections of NTFS and HFS+ on, which it turns on for itself, such as one through `.`, `..` or a folder that git, Windows or macOS opens as `.git`; it stops on a link in the copy before it reads or writes anything; it drops each git variable that names a repository, but the two that carry configuration; it stops, with and without `--check`, on a pinned file that holds a carriage return, which git would commit otherwise or the test of characters refuses; the refresh writes the whole copy in a folder of its own before it replaces the vendored paths, so that one that stops leaves the copy as it was; and it reads its lock with each carriage return before a line feed taken as a line feed. Its check compares the mode that git's index gives each vendored file, which is what a commit holds on any system, with the pinned commit's, and where a vendored file holds a carriage return that the pinned commit's does not, says to run the sync, or to delete the copy and check it out again. An attributes file that an update of upstream brings fails the tests until the owner decides whether the tests or the sync change.

## Alternatives

- Leaving line endings to each person's git, as the repository did: a clone made with `core.autocrlf` set to `true` fails the tests, and its hook and scripts do not run.
- Taking each carriage return before a line feed as a line feed in the checks alone, with no attributes: the checks would pass in such a clone, but the hook and the scripts would still not run there.
- Giving every file `-text`, so that git never changes line endings: a clone would hold what the repository's objects hold, but a file that an editor saves with carriage returns would be committed with them, and fail only once the test of characters reads git's index.
- Giving every file `text` rather than `text=auto`: git would take every file as text, an image or a PDF that a record lets in among them, and change its bytes wherever they read as a carriage return and a line feed.
- Holding carriage returns in the files that git stores: each check, and each checksum of a file, would read two forms of every file, and a diff that changes only line endings shows each line as changed.
- Rewriting a clone made before the line by itself, as a hook or a script that writes every file again: it would discard what a person had not committed, so the test names each script instead and gives the way back.
- Comparing the modes that the working tree gives the vendored files: a checkout on Windows, where `core.fileMode` is `false`, gives no mode to compare, while git's index keeps the mode that the commit gives.
- Running the sync through `git archive` with `core.autocrlf` turned off for it: `git archive` would still follow a `.git/info/attributes` that git's template gives a new clone, and upstream's own attributes, while git's objects hold the bytes that the pinned commit gives.

## Consequences

- The repository tracks a `.gitattributes` whose one line gives every file `text=auto` and `eol=lf`, and a test fails, naming the file and what its attributes give, when the attributes do not give a tracked file both, while R274's test of attributes still refuses any attribute but `text` and `eol` (R274, R276; task 1.54).
- A clone made with `core.autocrlf` set to `true` at a commit that holds the line holds what git's index holds, the hooks that `.claude/settings.json` registers among it, so that the session's start hook and the scripts run there and every test passes (R276; T256; task 1.54).
- A clone made so before the line keeps its line endings in each file that no later checkout writes. Each file there but a script and the vendored copy is read as git will commit it, the generated skills among them, which `scripts/verify-openspec.sh` compares with git's index by content; the test of characters, and for a vendored script the test of the files that others write, names each script that holds a carriage return and gives the way back, which keeps an edit not yet staged, the vendor check names each vendored file that holds one and gives the way back for the copy, and `CONTRIBUTING.md` gives both (R269, R275, R276; T267, T275; tasks 1.52 and 1.54).
- The checks of single pages, the test of characters, the test of the files that others write and `scripts/spec_form.py` read the working tree through the shared function, and the scenarios of R176, R210, R255, R268, R269 and R272 that named a carriage return name one that no line feed follows, one that git's index holds, or one in a script. A test that planted a carriage return before a line feed to show that a check fails plants one that no line feed follows instead, as those scenarios now give it, and the change that builds it says which (R276; T251; task 1.54).
- CI saves the repository's own files, but its scripts, with Windows line endings and runs `ruff check`, `ruff format --check`, `mypy`, the tests, `scripts/verify-openspec.sh` and `scripts/sync-superpowers.sh --check` there, so that a check which reads a file in another way fails there, and the job fails where it saved nothing, while no job or step there may be skipped or fail and the job `ci` pass, and the job writes through no link and into no file that others write (R276; T226, T269, T277; task 1.54).
- A test that plants Windows line endings fails where its checkout wrote line feeds, as the line would make a clone with `core.autocrlf` set to `true` write them, so the trials of the plugin's command and of its zip use a `.git/info/attributes` that gives `eol=crlf` (R276; T143; tasks 1.54, 2.6 and 6.6).
- The vendored copy holds the pinned commit's bytes and modes whatever the person's git converts, the sync writes nothing outside it, through a link or into a repository that a person's git variables name, stops on a pinned file that holds a carriage return, and leaves the copy as it was where a refresh stops, and `.editorconfig` gives the lock line feeds (R275; T268, T270, T273, T274, T278; task 1.52).
- An attributes file that an update of upstream brings under a vendored path fails the tests of attributes and of line endings, so the update waits for the owner's decision on whether the tests or the sync change (R274, R276; T276).
- A check that reads what git holds rather than the working tree, such as the comparison of each record with the default branch, reads no carriage return as a line feed: one that a commit holds is still a change, and the test of characters refuses it (T251).
- A script that an editor saves with Windows line endings does not run in bash, which reads each carriage return as part of its line. The test of characters names it with the reason, and git commits it with line feeds alone, so CI and every other clone are not affected.
- A clone of this repository's marketplace made at a commit that holds the line holds the plugin's capture step with line feeds too, whatever `core.autocrlf` says; the plugin's command still takes each CRLF as LF, so that a person's own attributes, and a clone of the marketplace made before the line, change nothing that it runs (R276; T143; DR-211).

## Scope

This covers the line endings of every checkout of this repository, of the vendored copy that its sync script writes, and how its checks read them. The characters that a file may hold are DR-274 (Everything that this repository writes holds printable ASCII) and DR-275 (The files that others write hold only the visible characters that a test lists), the attributes that the repository may set are DR-280 (The repository's attributes set nothing but line endings, and are read as git holds them), and how the tool's command reads the hook file and the plugin's capture step is DR-211 (The capture step runs only when its checksum matches, with each CRLF taken as LF). The line endings of the files that the tool writes in an adopter's repository, such as a ledger file, and git's refusal of a ledger file where `core.safecrlf` is on, are not covered here: they are a postponed point of B-007.

## What reversing it would change

How hard it is to reverse: reversible. The attributes are one line, the reading one function that the checks share, and the sync's copy one step of its script. R276 in `project-standards` would change, with its scenarios, and so would R275's scenario on the sync, the scenarios of R176, R210, R255, R268, R269, R272 and R274 that name a carriage return, the answers of T143, T226, T251, T256, T267, T268, T269, T270, T273, T274, T275, T276, T277 and T278, design decision 23 and tasks 1.52 and 1.54, and a clone made with `core.autocrlf` set to `true` would fail the tests again, with its hook and scripts not running. Nothing that adopters configure or depend on changes, so the change would not be a breaking one for adopters.
