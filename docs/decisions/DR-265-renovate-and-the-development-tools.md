# DR-265: Renovate proposes no newer development Python, merges nothing on its own, and notes how an update of OpenSpec or Superpowers is refreshed

- **Type:** technical
- **Status:** accepted
- **Decided by:** the change `add-pr-cost-calculator`, as the owner asked on 2026-11-19 and 2026-11-20
- **Requirements:** R259, R260, R261, R262
- **Threats:** T28, T34, T35, T66, T231
- **Replaces:** none
- **Closed by:** none

## Context

Backlog item B-003 asks for Renovate's configuration to keep the Python that the project develops on at the oldest supported release (DR-134), and to say that an update of OpenSpec or Superpowers has its generated files refreshed on its branch once its diff has been read. `.python-version` holds that release, and a test already fails a pull request that raises it alone, since every copy of the oldest supported Python must agree with the one that `pyproject.toml` requires, so that each newer release that Renovate proposed there would be a pull request that cannot pass. An update of OpenSpec or of the vendored Superpowers brings files that steer agent sessions, the generated `openspec-*` skills or the vendored skills and hook scripts, and its pull request at first changes only the pin, so that those files are refreshed on its branch after the owner has read that diff. A session on the branch would load and run them with the session's credentials before the owner has read them (T34, T35, T66), and a refresh made in such a session would run the new version, since `scripts/verify-openspec.sh` runs the pinned OpenSpec to write its skills again. The threat review at design also found that nothing kept a change to Renovate's configuration from letting it merge its own pull requests once the `ci` check passes, since the ruleset on `main` requires a pull request and that check but no approval (DR-072, DR-141, T231). The reviews before the merge found that the first checks let through a key of the `automerge` family other than `automerge`, a preset that another repository serves or that is written as one string, a later rule that turns `pyenv` on again, a setting outside the package rules that turns updates off, and a note's rule narrowed by another matcher. On 2026-11-20, shown that `ignorePaths`, `includePaths` and `allowedVersions` can each keep Renovate from proposing an update while the check of R259 passed them, the owner asked for a test that fails when `ignorePaths` differs from the list that the configuration holds, or when either of the others appears anywhere in it. A review of that test before the merge found that `packageFiles` and `ignoreNodeModules`, the older names that Renovate rewrites into `includePaths` and `ignorePaths`, passed it, that the tests read a file that gives a key twice, which Renovate refuses as a whole, and that a `prBodyTemplate` without the part of Renovate's own template that holds the notes would leave R261's note out of each pull request.

## Decision

Renovate's configuration has one package rule that matches the `pyenv` manager alone, which reads `.python-version`, and turns its updates off, and nothing else in it, at any depth, sets `enabled`, `ignoreDeps` or `enabledManagers`, the keys that turn updates on or off by name (R259), so that Renovate proposes no newer development Python while CI still tests the newest release beside the oldest. Nothing in it, at any depth, sets `includePaths` or `allowedVersions`, which narrow the files that Renovate reads and the versions that it proposes, or `packageFiles` or `ignoreNodeModules`, the older names that Renovate rewrites into `includePaths` and `ignorePaths`, and it sets `ignorePaths` only at its top level, to the list that its test holds, so that such a setting fails CI rather than resting on the owner's reading of the diff (R262). The configuration sets no key whose name begins with `automerge` to anything but `false`, at any depth, and extends, at any depth, no preset but those that its test lists, a preset written as one string included, since a preset that another repository serves can turn merging on later with no diff here, so that every update waits for the owner's merge (R260). A package rule that matches OpenSpec's npm package and Superpowers' repository by name, and by nothing else, gives each pull request that updates either a note: the owner reads its diff first; its generated or vendored files are then refreshed on its branch from a working tree outside any agent session's folder, and the owner reads the refreshed diff before merging; and no agent session starts on the branch before the owner has read its refreshed diff; nothing in the configuration sets a `prBodyTemplate`, which could leave the note out (R261). The root `CLAUDE.md` says that an agent refreshes such a branch's vendored or generated files only from a working tree outside its session's folder, so that the branch's context files and skills do not load into the session and its hooks do not run there, and that no session starts on the branch before the owner has read its diff as refreshed.

## Alternatives

- CI that refreshes the generated or vendored files and commits them to the update's branch: workflow tokens are read-only but for releases and the report's comment (DR-067), and a job that pushed would run the update's code with a token that can write.
- Renovate left to propose each newer Python, closed by hand: each would be a pull request that fails, which someone must read to close.
- A rule that turns off more, by a package's name, a file or an update type: it could silence updates that should come, which the test refuses.
- Merging left to the ruleset alone: the ruleset requires no approval, so an update set to merge itself would wait only for `ci`.
- A check of `enabled` in the package rules alone: a top-level `ignoreDeps` or `enabledManagers`, or a later rule that turns a manager on again, would get past it.
- Settings that narrow what Renovate proposes left to the owner's review of each diff of `renovate.json`, which R134 keeps visible: such a setting shows only in that diff, and the updates that it keeps back never show at all.
- A check of every setting that can hold back or narrow what Renovate proposes: Renovate has many more, such as its schedule, `minimumReleaseAge`, `rangeStrategy`, `dependencyDashboardApproval` and a package rule's `followTag`, `versioning` or `registryUrls`, which stay with the owner's review; the test holds the three that the owner named, and the older names that Renovate rewrites into two of them.
- A list of the presets that may not be extended: a preset that another repository serves can turn merging on later with no diff here, so the test lists those that may be.

## Consequences

- DR-145 still holds, and this record adds to it: a session starts on a dependency-update branch only once the owner has read its diff as refreshed, and the note repeats it on the pull request that the owner reads.
- The refresh runs the new version of OpenSpec or Superpowers with the credentials of whoever runs it, once the owner has read the update's diff and Renovate's wait has passed. The folder outside the session keeps the branch's context files, skills and hooks out of the session, not the new version from running (T66).
- DR-111 and DR-028 still hold: a major update waits for the owner's approval on the dependency dashboard, and minor and patch updates and vulnerability fixes are proposed as before.
- An update of OpenSpec or Superpowers is refreshed by running `scripts/verify-openspec.sh` or `scripts/sync-superpowers.sh` on its branch in a working tree outside any agent session's folder, and the refreshed files reach the pull request in a push that the owner reads before merging.
- A test reads Renovate's configuration for each of the three rules and the list of paths that it skips, and fails on a file that gives a key twice, which Renovate refuses, so that no test reads a value that Renovate would not.
- A real need to narrow what Renovate proposes, such as holding back a tool whose later release drops Python 3.11, changes the test in the same diff as the configuration. Renovate's other settings that hold back or narrow what it proposes, such as its schedule, stay with the owner's review of the diff of `renovate.json` (T28), and so does what the preset `config:best-practices` brings, which Renovate expands as it runs, from presets that its own releases change (A30). A setting that widens what Renovate proposes, such as a package rule's `replacementName`, or `registryUrls` that name another registry, stays with that review too, and each update that it brings still arrives as a pull request that only the owner merges (R260, DR-080).

## Scope

This covers what Renovate proposes and merges, and how an update of OpenSpec or Superpowers is refreshed. When a session may start on a dependency-update branch is DR-145 (A session starts on a dependency-update branch only after the owner reviews its diff), and when the oldest supported Python rises is DR-134 (The oldest supported Python rises only near its end of life or for a security fix).

## What reversing it would change

How hard it is to reverse: reversible. The three rules and the list of paths that Renovate skips are lines of `renovate.json`, held by R259 to R262 and their tests, beside a sentence of the root `CLAUDE.md`, and the answers of T28, T34, T35, T66 and T231 would change.
