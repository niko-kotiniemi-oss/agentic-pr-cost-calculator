# Spec Form Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build tasks 1.23 and 1.24 of `add-pr-cost-calculator`: `tests/test_spec_form.py`, which reads every spec that OpenSpec reads and fails on each defect of form that task 1.23 lists, and the comparison in `scripts/verify-openspec.sh` of that reading with what the pinned OpenSpec CLI lists and shows.

**Architecture:** One standard-library module, `scripts/spec_form.py`, finds the specs as OpenSpec finds them, checks each spec's bytes as plain text, reads its lines into requirements and scenarios as OpenSpec reads them, and returns the problems of form, each naming the spec and the line. The test runs it on the repository and plants each defect in a synthetic tree. The same module holds the comparison: it runs the CLI's `list` and `show` commands, reads their JSON, and compares each spec's and change's requirements, in order, with its own reading. `scripts/verify-openspec.sh` runs the comparison in CI's `openspec` job, where the CLI is installed; pytest tests it on output that the pinned CLI printed for synthetic trees, recorded in `tests/spec_form_openspec.json`, and through a stand-in CLI, so that no test needs Node.

**Tech Stack:** Python 3.11 standard library, pytest, and the pinned OpenSpec CLI in the `openspec` job.

**Spec:** `openspec/changes/add-pr-cost-calculator/specs/project-standards/spec.md`, requirements R173 to R178 with their scenarios; tasks 1.23 and 1.24; design decision 12; DR-193 to DR-196; the threats T124 to T126; the assumptions A9 and A32.

## Global Constraints

- `scripts/spec_form.py` uses the standard library alone and supports Python 3.11, since the `openspec` job runs it with the runner's own `python3` and installs no package for it.
- Tests never use the network, and none runs Node: the comparison's tests read recorded output and run a stand-in CLI written in Python.
- No line of a spec starts a line of output (T126): each problem and each difference starts with a path that the module's own walk found, and every path, name or text taken from a spec or from the CLI is shown with each character outside printable ASCII replaced by its code point.
- The module never follows a symbolic link in `openspec/` and never reads `openspec/changes/archive/`.
- Every pattern matches a line in one way only, and a test times each of them, and the reading of a whole spec, on lines of 40,000 spaces and of many runs of backticks.
- The test is stricter than OpenSpec only where DR-193 and DR-195 say. Where the build finds another place, the change's records say so before the code holds it.
- Each figure in a page, a comment or a commit message is computed in the session that writes it.

## How the pinned OpenSpec reads a spec

Read in the code of OpenSpec 1.14.1, under `node_modules/@fission-ai/openspec/dist/`, and seen on synthetic trees on 2026-11-09:

- **Which files.** `utils/spec-discovery.js` walks a specs folder, skips every entry whose name starts with a dot, does not follow a folder that is a symbolic link, follows a `spec.md` that is one when its target stays in its folder, ignores a `spec.md` at the top of the folder, and gives each spec the id of the folders below the specs folder, joined by `/`, sorted by code point. `list --specs` reads `openspec/specs/` so. `list` lists every folder in `openspec/changes/` but `archive`, dot folders among them, while `validate --all` skips the dot folders. `show <change> --json` fails on a change with no `proposal.md`, though `validate` reads its specs.
- **A main spec.** `show <spec> --json` reads it with `core/parsers/markdown-parser.js`: it strips a byte-order mark, turns each carriage return into a line feed, splits at line feeds, and masks every line from one that starts, after any whitespace, with three backticks or tildes to the line that closes it. A heading is a line of one to six `#` signs, whitespace and text. The first section titled `Requirements`, in any case and at any level, holds one requirement for each heading below it: its name is the heading's text without `Requirement:` and without a closing run of `#` signs; its text is the lines before its first heading below it that are not blank, each trimmed, joined by line feeds, leaving out a line that starts with a bold label and a colon when other lines remain, or else the heading's text; and its scenarios are the headings below it whose body is not empty, each with its name and its body, trimmed, as `rawText`.
- **A change.** `show <change> --json --deltas-only` reads each spec of the change with `core/parsers/requirement-blocks.js`, which takes `###Requirement:`, with no space, for a requirement's heading too, and gives, for each spec in id order, the requirements of its `ADDED`, `MODIFIED` and `REMOVED` sections, each in the order the spec gives them, then its renames, each a `FROM:` and a `TO:` line. Each requirement is read as in a main spec.

## The form that the test allows

A spec is read line by line, a line ending at a line feed alone. Its lines are, in order:

- an optional title, `# ` and its text, before any section, which in a main spec is not `Requirements` in any case, since OpenSpec would read it as that section;
- sections, each `## ` and its name, spelled as here: in a main spec `Purpose` and `Requirements`, each once; in a change's spec `Purpose`, once, and `ADDED Requirements`, `MODIFIED Requirements`, `REMOVED Requirements` and `RENAMED Requirements`;
- in `Requirements`, `ADDED Requirements`, `MODIFIED Requirements` and `REMOVED Requirements`, blank lines, then requirements, each `### Requirement: ` and its name, its text, and its scenarios, each `#### Scenario: ` and its name, then its lines;
- in `RENAMED Requirements`, blank lines and pairs of lines, `` - FROM: `### Requirement: <name>` `` and then `` - TO: `### Requirement: <name>` ``;
- in `Purpose`, lines of prose, and before the first section, blank lines alone but for the title.

A scenario's lines that are not blank are one `- **WHEN** ` line, any `- **AND** ` lines, one `- **THEN** ` line and any `- **AND** ` lines. Trailing spaces and tabs on a heading, and a closing run of `#` signs after a space on a requirement's or a scenario's heading, are allowed, since GitHub and OpenSpec both leave them out of the name. No other line starts, after any spaces, tabs or list or quote markers, with `#` or with three backticks or tildes, or holds only `=` or `-` signs, since GitHub would show a heading or a fence there that OpenSpec does not read.
