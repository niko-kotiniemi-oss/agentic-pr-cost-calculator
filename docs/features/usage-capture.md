# Usage capture

While a Claude Code session works in the repository, a hook records what each model call spent, and the agent's own commits carry it to the pull request in ledger files. Nothing is sent anywhere: what the hook records stays on the machine until a commit takes it. The hook comes two ways: from the hook file that a repository copies and registers for everyone who works in it, or from the plugin, which a person adds for themselves and which is how a project's cloud threads are recorded.

**Status:** designed, not built yet.

**Spec:** `usage-capture`

**Requirements:** R2, R75, R41, R42, R43, R44, R165, R45, R167, R111, R3, R147, R76, R180, R197, R5, R7, R148, R78, R46, R47, R8, R79, R80, R81, R82, R83, R84, R85, R86, R48, R112, R49, R50, R51, R9, R87, R52, R113, R114, R115, R116, R117, R11, R181, R191, R192, R12, R53, R54, R169, R118, R13, R88, R179, R89, R90, R55, R149, R170, R150, R151, R152, R153, R154, R155

## Expected behaviour

- **What is recorded.** For each model call, once: its UTC day, its model, a hash of its message id, whether the main agent or a subagent made it, and its input, output, cache-write and cache-read tokens. Where the transcript gives them, it also records the attributes that change the price: service tier, speed, inference region and server-side tool requests (R2). A call is recorded only when it was made while both switches were on, as the [opt-in's page](switch-and-opt-in.md) says (R40).
- **Placed by the line it answers.** R165 gives how a run reads again the lines that earlier runs read, so that a call is placed inside or outside an interval by the line it answers, whichever run read that line, and what the next ledger file says of a call that it leaves out.
- **Where from.** R147 and R169 give how a call's repository and worktree are told, by the working directory that its transcript line gives, alone. R76 and R180 give the repositories that a run of the hook file's registration and a run of the plugin work on (DR-198), and R197 where a run of the plugin lets git start a program that a repository's configuration names, so that a clone that the session only meets or moves into has git start none of the programs that its own configuration names, such as `core.fsmonitor` or `gpg.program`. A run that works on a repository records there only the calls made in it or in one of its worktrees (R3, R180). That rule has limits:
  - A call made here that works on another repository, through an absolute path, `git -C` or a `cd` inside a command, is recorded here, and a call made in another repository that works on this one is not. So work on other repositories, private ones above all, belongs in sessions of its own.
  - A repository nested inside this one's folder is not this one, and neither is a folder that contains it, so the calls made from either are not recorded here, though the plugin records the nested one's from the first run that meets it, and a session should start in the repository.
  - A call whose line gives no working directory, or whose directory is gone or names no repository that git can tell by the time a run reads it, as when a worktree is removed first, is left out. When the line gives no directory, or a directory inside this repository's folder, where Claude Code keeps its worktrees, or a folder that holds this repository's folder, as a project's cloud thread's folder holds its clones, the session's next ledger file here says that calls whose repository could not be told were left out, with no count (DR-199, DR-200). Any other directory raises no flag, so no ledger file tells of work in another folder.
  - A run reads a call some time after it was made, at the session's next run. A path that holds another worktree or another repository by then sends the call there, so a run comes before and after every git command that the hook's condition matches, to keep that gap short.
- **Which branch.** R78 gives the branch that a call goes to (DR-012), and R7 the run before every git command that the hook's condition matches, so a call reaches another branch only when it is the call that runs that command and its run cannot yet read it as over, when that run's time budget leaves it unread, or when the branch changes in a way that the condition does not match, as the design's risks list.
- **The store.** Between runs, capture keeps its notes in a store: one file for each user, in a folder of that user's own, `pr-cost-<uid>/store.json` in the repository's git common directory where the system numbers users, as POSIX systems do, and `pr-cost/store.json` where it does not, outside the working tree, shared by every worktree and never committed. R149 and R170 give what it holds, and which of it only as SHA-256 hashes, and R4 that none of it reaches a ledger file, and the store never leaves the git common directory.
- **For 30 days at most.** The store's retention window is 30 days. R150 gives what a run drops and takes back at that window, R155 what the next ledger file then says, and R151 that a store that holds nothing removes itself. Retention runs at every run that finds a store of a version that it knows, whatever the switches say, and only then, so a repository where no session runs again keeps its store until the person removes it.
- **For its owner alone.** R152 gives how each write leaves the store's folder and file for its owner alone, mode 0700 and mode 0600, and the stores and notes that a run leaves alone. A run that cannot make its store's folder records nothing. On Windows, the step checks neither the store's access list nor its owner, so there the store has the access of the git common directory around it.
- **A removed store.** R153 gives what a store that the person removes, or that does not parse, as when a sync or a power loss cut it short, takes with it, and when a store does not parse, and R145 and R153 what a run does with such a store. A ledger file staged before the removal stays staged, left to git, so that the next commit takes it (R153). So before removing the store, look for a staged ledger file with `git status` in every worktree that `git worktree list` names. A session resumed in a fresh clone at the same path, which holds no store, records none of the calls that answer a line written before its first run there.
- **A clone that git does not trust.** git refuses to work in a repository whose folder another user owns, unless a `safe.directory` setting names it, so capture records nothing there, with no flag, until one in the person's global configuration, or the system's, does. Capture runs git without the session's `GIT_` variables, so a setting that only they give does not count. Adding one to the person's global configuration ends every open interval in their other repositories, as any write to it does.
- **Worktrees that capture leaves out.** Before it starts any program, capture reads the project directory's `.git`, the `commondir` file of the git folder that it names and each linked worktree's `gitdir` file itself, to learn which folders hold the repository's working trees, so that it never starts a git that one of them holds. A run that cannot read one of them, finds a folder in `worktrees/` with no `gitdir` file, or runs in a linked worktree whose git common directory is not named `.git` records nothing, and says so on standard error. So capture records nothing in a submodule's linked worktrees, in a linked worktree of a repository whose git folder was moved to a folder of another name, or in any worktree of a bare repository in a folder not named `.git`, such as `repo.git` or `.bare`, as when a person keeps a bare clone with a worktree for each branch (DR-188). A bare repository in a folder named `.git`, as `git clone --bare <url> proj/.git` makes one, is taken to have its main worktree in `proj`, as `git worktree list` takes it, so capture records in its worktrees as in any linked worktree.
- **No transcript kept.** Capture writes no line of a transcript, and no value from one beyond an entry's fields and the store's notes, to any file or to standard error (R154). A pull request's cost is recomputed from its ledger, the price table and GitHub's jobs API alone, and keeping or reprocessing transcripts would need a change of its own (DR-178).
- **When.** R7 gives the events at which the hook runs, and R148 what the start run does. The plugin's run when a session ends takes back first, as R90 gives it, and stops within the 1.5 seconds that Claude Code gives a plugin's `SessionEnd` hooks, which a plugin cannot raise.
- **The plugin.** The tool also ships the capture step as a Claude Code plugin, which a person adds from a release's zip or from the tool's repository as a marketplace (DR-203). R179 gives how its hooks run the same file as the hook file's registration, only when its SHA-256 matches, so that neither a branch checked out during the session nor, for a plugin loaded in place from a folder, a change to that folder's file changes what it runs (DR-197), and R188 what its manifest and hooks hold. It runs wherever it is loaded, in a repository that registers the hook or not, and records only where the tool is on and the person has opted in.
- **Two copies in one session.** A session can run the plugin and the hook file's registration together, their runs coming in parallel at each event, while of two copies of the plugin, as when a person adds it both ways, only one registers its hooks. R181 gives how both copies share each repository's store, so each call is recorded once and each commit gets one ledger file at most, R192 how every release writes a store version the same way, and R191 how a copy of an earlier release leaves a session to the later one, but for an opt-out, which it acts on, and R55 how a copy leaves alone a store of a version that it does not know. Once the later copy no longer runs there, as when the person removes the plugin, the earlier one records nothing in that clone, with no flag, until it is updated (DR-206).
- **A project's cloud thread.** A project's cloud threads run none of the hooks that a repository's settings register, so capture runs there only through the plugin, which the person adds in the project's settings and which loads into the threads that start afterwards, not into those already running. A person opts in there with one line in their environment's setup script, `git config --global pr-cost.capture true` (DR-201). A thread starts in a folder that holds each of the project's clones and is in no repository, and many of its calls, its subagents' among them, name that folder until Claude moves into a clone, and again whenever Claude's current directory goes back to it, as after a pause and resume, so they are left out and flagged, and the comment says that the figure is a lower bound, never by how much (DR-199). A call made from inside a clone counts in that clone, whatever clone it reads or changes through paths or `git -C`, so a project that holds a repository that turns the tool on should hold no repository whose work must stay private. To keep a thread's work inside a repository, ask Claude, as in the project's instructions, to work from inside the clone: one `cd` into it does not keep a thread there, since Claude's current directory can go back to the thread's folder. A thread's machine pauses after a turn and resumes with its files, while one that cannot be resumed continues from a fresh clone, which holds no store, so the calls that no commit took are lost with the old machine: committing as the work goes keeps them.
- **How it reaches the pull request.** Just before the agent's `git commit`, the hook writes the waiting calls of that commit's worktree and branch into one new ledger file, with the flags due there, and stages it, so that the commit takes it. It does this only for a commit whose branch and contents it can tell from the command. Otherwise the calls wait for a later commit.
- **When no commit takes the file.** If the commit fails, is refused at a permission prompt or by a permission rule, is cancelled or never runs, the hook takes the file back, and its calls and flags wait for a later commit (R9, R87).
- **Removed calls stay removed.** Once a run has found a commit holding a ledger file, the hook never stages that file's calls again in that clone, so a ledger file removed after that takes its calls with it (R52).
- **Counts are checked.** R5 gives the counts that capture refuses, and the ledger says how many calls were refused.
- **Two runs at once.** Runs at the same time, such as the main agent's and a subagent's, never split each other's notes or record one call twice (R11).
- **It never gets in the way.** A failure in the hook never stops the session. The hook prints nothing that Claude reads, writes no transcript text anywhere, and stops at a time budget, leaving the rest for its next run (R13, R90, R154).

## Not covered

- Commits the hook cannot follow: `git merge`, `git cherry-pick`, `git rebase --continue`, a script, an API, a commit in the background, in a pipeline, a subshell or a group, joined by `||` or behind a wrapper, and commits made through Claude Code's PowerShell tool. Their calls wait, and may reach no pull request. The design's risks list every such case.
- Agents other than Claude Code.

## How it is validated

This feature is validated first by its spec's scenarios: each gets an acceptance test before its code, seen to fail for the expected reason (task 1.4). Then come the checks that DR-084 to DR-093 and DR-109 apply to all the tool's code. Beyond those, this feature has its own:

- Synthetic transcripts and hook inputs in each shape that Claude Code writes, with the lines for commands refused at a permission prompt or by a permission rule, and for blocked, cancelled and interrupted ones, checked against what Claude Code writes for them, and with calls made in another repository, in a repository nested in this one, in its worktrees and with no working directory, and calls that work on another repository through an absolute path or a `cd` inside a command (task 1.1).
- The store's format, field by field, with each field's purpose and how long it is kept, the retention window and the store's modes, written down before the code, with the tests reading those values from it (task 1.2).
- Unit tests at every boundary of the counts, and property tests that no planted string reaches the ledger or any file but the store's note of a staged ledger file, and that a second run changes nothing (task 2.1).
- Tests of the store: that it holds ids and paths only as hashes while no file is staged, keeps a staged file's names only until a run resolves it, keeps nothing past its retention window and flags the waiting calls it drops, removes itself once it holds nothing, is left for its owner alone at each write, is left alone when it is a link, another user's or of a version that the run does not know, and is treated as removed when it does not parse (task 2.1).
- Tests against real git of the commits that the hook follows and of those it does not, those refused at a permission prompt or by a permission rule, cancelled or interrupted included (task 2.2).
- What the README's section on adopting the tool says about how git treats a ledger file, tested with the CI runner's git and, in a CI job of its own, with git 2.43 (task 4.4).
- The hook run from another directory and in each shell that its registered command meets, Windows PowerShell included, and a start run that reads no transcript and prints nothing (task 2.3).
- The plugin's hooks held to the hook file's registration, read from every file that can declare them, its command run in each shell with its script missing or changed, a plugin run's repositories in a folder that holds two clones, three with one unreadable, and with a repository nested in another that a `git -C` command reaches, the plugin and the hook file's registration run in one session, in parallel, of one release and of two, and a fixed store version's fingerprint held to the one recorded for it (tasks 2.6 and 6.1).
- The plugin in a project's cloud thread, added from a release's zip and from the marketplace, with the opt-in in the environment's setup script, and calls made before a pause reaching a commit made after it, checked by hand (task 7.2).

## Known limitations and the roadmap

The design's risks that concern this feature and are not on the roadmap, each with what it means:

- **Claude Code changes its transcript format**: a change shows up as refused calls, counted, rather than as a guess, until the parser learns the new shape.
- **A call read without a stop reason gives the usage of its start, not of its end**: such a call's output tokens are too low, and the comment says that the token cost is a lower bound.
- **A call is recorded on the branch checked out when it is recorded, which can differ from the one it was made on**: in three narrow cases a call can be counted on another branch than the one it was made on.
- **A git add that stages nothing comes before a commit that would otherwise commit nothing**: the commit holds the ledger file alone, where without the tool it would have failed.
- **A commit is refused at a permission prompt or by a permission rule, blocked, cancelled or interrupted after its ledger file was staged**: the ledger file stays staged until a later run of the capture step takes it back.
- **A git command starts while a run stages or takes back a ledger file**: that git command fails at the index lock, as when any two git commands meet.
- **A person removes a ledger file from their branch, or a commit that holds one is undone**: the calls in that file are not counted again unless the file itself is committed again.
- **A repository's own git hooks see the staged ledger file**: a hook that refuses the file fails a commit that would pass without the tool.
- **A repository's settings act on the ledger path**: where an attribute would change the file, capture stages nothing, and the comment says that no agent usage was recorded.
- **A session is resumed in a fresh clone at the same path**: the calls answered before the fresh clone's first run are left out and flagged.
- **Capture fails without anyone seeing it, since a hook that succeeds shows nothing**: refused calls are counted, and a pull request whose capture never ran says that no usage was recorded.
- **A worktree is removed, or another repository put at its path, before a run reads the calls made in it**: a removed worktree's calls are left out, and a path that now holds another repository sends them there.
- **The store is removed while a ledger file is staged**: the next commit in that worktree takes the file, with calls recorded with consent.
- **A ledger file that the plugin stages in a repository that the session then leaves stays staged**: the file stays staged until a later run of that session meets that repository.
- **Two releases of the hook meet one store, as when sessions start in two worktrees that hold different releases, or a session runs the plugin of one release and the hook file of another**: a run of a release that does not know the store's format records nothing, so those calls are not counted.
- **A backup or a sync puts back an earlier copy of the store, or two users of one clone meet**: a copy put back can bring back waiting calls when the opt-out came only through the environment.
- **The hook file in the working tree changes during a session, as when the session checks out a branch that updates the hook**: the capture step stops for the rest of the session, so its calls are not recorded, unless the session is resumed once the registration and the hook file agree again.
- **A checkout changes the capture step's bytes, as git does to its line endings where `core.autocrlf` is on, so that its checksum stops capture without a flag**: capture stops without a flag where a person's own filter changes those bytes.

The [roadmap](../roadmap.md) gives what is planned next and later, and the limitations that an adopter notices.
