# Standards for the whole tool

What holds for the whole tool rather than for one feature: documentation that names everything the tool does, connections only where that documentation says, rated threats, pull request text without private references, action pins that their repositories tagged, a record of each decision, the assumptions that the design rests on, a glossary of the words its documents use, specs that OpenSpec reads as they are written, a roadmap and the backlog items that it indexes, a guide to how the project builds, and a golden set of figures that every version reproduces.

## Expected behaviour

- **Documentation.** A register of every requirement, one page per feature, and [`../how-it-works.md`](../how-it-works.md), which names every credential, permission, connection and flow, each held by the tests that R29, R100 and R101 give.
- **Validation, written down.** R73 and R74 give the page that each feature has, with all its requirements and how it is validated, what each change's proposal says of each capability, and the tests that hold both.
- **The specs' form.** R173 to R178 give how every spec that OpenSpec reads is read as OpenSpec reads it, line by line, so that none is read otherwise than it is written or shown, and how CI compares that reading with what the pinned OpenSpec shows.
- **What the opt-in publishes, and where it applies.** R159 and R164 give what the README, the opt-in's feature page and the ledger's say of what an opt-out leaves published, what a hashed id does not hide and where an opt-in applies, with the glossary's word to avoid, and R204 what the README says of who sets an opt-in.
- **Cloud threads, organizations and the plugin.** R185 gives what the README and the capture's feature page say of how capture covers a project's cloud threads, R194 what the README says of turning capture off in a session that is running and of checking it, R186 what it says of an organization's option, R187 the two ways to install the plugin that it gives, the zip first, and R195 and R196 what it says of which release of the plugin runs and where a refused commit can leave a ledger file staged.
- **The README's short start.** R198 to R201 give the short start that the README opens with, what it says before any step that opts anyone in, the sections of detail folded below it and the addresses that the README may give, R203 where its section on adopting the tool takes the tool from, and R205 what its status says while this repository's root marketplace file holds no entry for the tool's plugin, each with the tests that hold it.
- **The backlog and the roadmap.** Planned work is kept as backlog items in `docs/backlog/`, indexed by `docs/roadmap.md`, as R206 to R211 and R213 to R218 give them, with the tests that hold both.
- **The briefing for developers.** R212 gives the briefing that the README's section on working on this repository opens with, and its table of the stages of the work, which `CONTRIBUTING.md` and the backlog's page link rather than repeat.
- **The guide.** A guide, `docs/patterns.md`, says how the project builds, concern by concern, and steers below the specs and `CLAUDE.md`, as the default branch holds it, from an opening that its spec gives word for word. Each entry says where the project stands: followed, designed, knowingly accepted or a gap, each gap naming the backlog item that closes it, a gap whose item is under the roadmap's Now holding the build back, a principle, or the concern that it stands under, changing alone, a gap given to an agreed item changing that item, and a gap closing only with its item, as R219 to R222, R226 to R228, R231 and R233 give it.
- **No capture here before its time.** This repository holds no switch and no ledger file until task 7.1 turns the tool on here, and no reusable workflow until task 4.3 gives it its guard on events, as R223 and R229 give it. These checks and the guide's read each change's tasks as GitHub shows them, each given once, as R232 gives it.
- **The walking skeleton.** The walking skeleton, in `skeleton/`, is the thinnest path from a session's calls to the report's figure, run once in a scratch repository before the build. Nothing here registers it, it records only with its own switch and the person's opt-in and only the calls made in its repository, it never stalls or steers the agent, it stages only for a commit that it recognises, its report counts one merged pull request's calls once at a test price, its workflow can do no more than post its comment, its plugin declares nothing but its command hooks, its files and the README say what it is, the transcript shape kept from its run holds no values, and no release holds it, as R234 to R243 give it.
- **Which agents an opt-in records.** The README's short start, its section on the opt-in and the opt-in's feature page say which agents an opt-in records, and its section on organizations has an organization tell its members, as R199, R224 and R186 give it.
- **Connections.** The hook opens no network connection. The report connects only to GitHub, over HTTPS, with the workflow's own token: to its REST API, at the address the workflow gives, and by git to the tool's own repository and the one it reports on. Prices are read from the price table in the repository and never fetched (R30).
- **Threats.** Every threat in [`../threat-model.md`](../threat-model.md) is rated and placed in the risk matrix as R31 gives it. The threat model is reviewed independently before a design is approved, and again against what was built before its pull request merges.
- **Pull request text.** R33 gives how a pull request's title and body are checked against the same private patterns as the repository's files, and what a match does.
- **Pinned actions.** Every action and container image that a workflow uses is pinned as R34 gives it.
- **Decision records.** Each decision has a record of its own in [`../decisions/`](../decisions/README.md), as R124 to R134 give it, with the index that lists every record and the tests that hold both. A record that the default branch holds changes only by being closed, so each decision can be reversed on its own and its history stays readable. Threat IDs, like requirement IDs, are retired rather than reused, so a record never comes to cite another threat.

- **Assumptions.** Every assumption that the design rests on is in [`../assumptions/`](../assumptions/README.md), as R135, R136, R140 and R143 give it, with the tests that hold them.
- **Words.** A glossary, `docs/glossary.md`, gives each term's meaning and the words to avoid for it, with the tests that R137 and R138 give. Words inside code are left as written, so a name that adopters type keeps its spelling. A script, `scripts/rewording.py`, run from the copy that the default branch holds, lists for the owner and the review each line that a rewording changed by more than a word to avoid replaced with its term, apart from those each line that replaces a word that the glossary at the pull request's base did not give for its term, and each changed file that it does not compare, and refuses to compare when the glossary is not in its form. The glossary and the assumptions describe, and never steer: where they differ from `CLAUDE.md` or a spec, those hold.
- **Golden set.** R139, R141 and R142 give the golden set of synthetic sessions, worked out by hand from the specs, that every version must reproduce, and when a golden figure may change.

## Not covered

- Whether a threat's answer still says what holds it. The tests check that each citation resolves; the reviews at design and before merge check what it says.
- Whether an assumption is true. Its entry says how each fact is checked, and the check is no stronger than the test, the observation or the documentation that it names.
- Whether a word with several senses is used in the right one. The glossary defines it, and the reviews check its uses.
- Whether a meaning in the glossary narrows a rule without contradicting its words. The owner's review of the glossary's diff checks that.
- Whether a rewording changed what a rule says. The rewording script lists every line that changed by more than a word to avoid replaced, and the owner and the review read them.
- Whether a setting on GitHub that the owner keeps is still as the threat model lists it. No test may read one, so the assumptions list each as not yet checked.
- Whether a decision record holds one choice, describes rather than instructs, and says what its sources say, and whether the owner made a decision that a record attributes to the owner. The reviews check the first three, and the owner checks the last before merging.
- Whether a requirement states one behaviour, and whether its scenarios test what it says. The reviews check both; the test of the specs' form reads only their form.
- Whether the guide's principles are right, whether a source says what an entry says it does, and whether a gap's backlog item really closes it. The reviews check them.

## Known limitations and the roadmap

The design's risks that concern this feature and are not on the roadmap, each with what it means:

- **Mutation testing takes time in CI**: how long it takes is measured when it is added, and what to do about it is decided then.
- **A rewording changes what a requirement, a scenario, `CLAUDE.md`, a threat's answer or an instruction to adopters says**: a rewording could change what a rule says, so it changes no text that it must not.
- **An assumption's check claims more than was checked**: a check could claim more than it showed, so each one names what holds it.
- **A golden figure is changed to agree with a defect**: a defect could be hidden as an expected figure, so a golden figure changes only beside the spec that changed it.
- **The glossary, an assumption or a page that one links to reads as an instruction to an agent**: such a page could steer an agent, so they describe and never instruct.
- **The walking skeleton's run shows that a fact the design takes from Claude Code is wrong**: the design would rest on a wrong fact, so what the run shows goes into the assumptions and the specs before the build starts.
- **The walking skeleton leaves out most of what the design asks**: the skeleton is not the tool, so the design lists each part that it leaves out, and no release holds it.

The [roadmap](../roadmap.md) gives what is planned next and later, and the limitations that an adopter notices.
